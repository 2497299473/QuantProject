## 第一步 交易日守卫

读 `D:\PythonProject\QuantV1\data\holidays.json`（结构 `years.<年>.<节日>→日期数组`，仅含周一~五休市日，周末由本步过滤）。

Get-Date 取今天：

- 周六/周日、或今日出现在任意年份休市集合 → 只回一句「日汇总：<日期> 非交易日，无任务需检查，跳过」，不写任何文件，结束。
- 若当前年份不在 years 键中 → 该句后补「⚠️ holidays.json 未覆盖 <年份> 年，请每年 12 月更新」。

## 第二步 待汇总清单（顺延/补漏）

今日（若为交易日）必入列。

另从今天往回最多 10 个自然日内的每个交易日 D（且 D ≥ 2026-09-09，OpenSquilla 接管起点）：

- `daily_runs\<D>.md` 存在但无「[23:00 日汇总]」小节 → 入列（补做）
- D ≥ 2026-09-09 且文件不存在 → 也入列（记「当日无任何运行记录」）

按日期先旧后新逐个执行第三步。

## 第三步 对每个日期 D：完整性检查 + 摘要 + 写文件

1) **OpenSquilla 调度库证据**（只读；09:30 晨检无文件产出，执行证据只有这张表）：

   ```
   Set-Location -LiteralPath 'D:\PythonProject\QuantV1'; .\.venv\Scripts\python.exe -X utf8 daily_runs_tool.py runs --date <D>
   ```

   该工具已内置「UTC 存储 → +08:00 归一」的日期过滤与逐 job 最新一次取值，**禁止再自己写 SQL 或按字符串自行过滤**（2026-09-17 事故：`scheduler_runs.started_at` 存的是 UTC ISO，按北京日期串匹配永远查不到 16:00 实例 → 误报「未执行」）。输出四行，`当日无记录` 即真无。job_id 前缀对应：93439da7=09:30 晨检、fa6d9cdd=16:00 板块K线、69b20a70=22:30 Shadow、ed7ae8c8=23:00 日汇总（本任务自身）。库里 success 列仅供参考，是否跑完以文件小节为准。

2) **文件证据**：读 `D:\PythonProject\QuantV1\output\daily_runs\<D>.md`（不存在→按全部缺失处理，第 6 步仍要建文件留痕）。检查小节：[16:00 板块K线]、[21:30 板块K线补拉]、[22:30 Shadow]；若 D=2026-09-28 另查 [09-26 季度重估] 小节。

3) **Windows 侧证据**：Get-ScheduledTaskInfo -TaskName QuantFund_KlineEvening（21:30 补拉是 Windows 计划任务，不在 OpenSquilla 库里），看 LastRunTime 是否落在 D 当天。

4) **判定口径**（每条任务一行）：

   - 跑完 ✅ = 当日小节存在
   - 触发未完成 ❌ = 当日有 started_at 但文件无小节（标注「已触发但超时/未完成」）
   - 未触发 ❌ = 库与文件皆无（标注「未触发——检查当时电脑是否唤醒、gateway 是否在跑，必要时手动补跑」）
   - 若 22:30 当日有 started_at 无 finished_at（仍在跑）：Start-Sleep 最多 300 秒后重查一次文件再判定。

5) **摘要口径**（每小节一行，异常才展开两三行）：16:00 的 ok/skip/fail、FAIL 码、是否走 Playwright 兜底、新浪校验一行结论；21:30 的 ok/skip/fail 与一句话结论；22:30 新增条数或全部幂等跳过、ADD/REDUCE/HOLD 分布（出现 ADD 或 REDUCE 显著标注）；09:30 晨检是否跑（库证据）。

6) **写入**（必须执行，无论检查结果好坏）：**只能通过追加工具写，禁止自己读文件再整份重写**（2026-09-17 事故：读-改-写把当日 [16:00]/[21:30] 小节抹掉且 [23:00] 写了两份）。做法：先把小节正文（不含 `##` 标题行）写入临时文件，再执行

   ```
   Set-Location -LiteralPath 'D:\PythonProject\QuantV1'; .\.venv\Scripts\python.exe -X utf8 daily_runs_tool.py append --date <D> --section "[23:00 日汇总]" --file <临时文件>
   ```

   工具只 append、同名小节已存在则 SKIP（幂等），目录不存在会自动创建。补做的日期在正文首行写「（顺延补做，实际执行 <今天日期>）」。小节末尾固定一行「需人工介入的点：…」（缺小节/未触发/FAIL/超时清单；全部正常则写「无」）。SKIP 出现 = 说明本小节已写过，检查是否重复执行，不要 --force 强行再写。

## 第四步 待拍板清单（Summer 每天唯一需要行动的部分）

从本次检查的所有日期（含顺延补做日）中筛出需要 Summer 拍板的事项，写入汇总小节末尾，并进入最终回复。

**入列标准（满足其一）**：

- 单日无法自愈、且连续 ≥2 个交易日复现的异常（同一 FAIL 码、同一任务反复超时/未触发等）→ 是否换通道/改任务结构/加兜底
- 必须改生产 .py、config.json 或定时任务表才能解决的事项（本任务铁律禁止自改，只能提请）
- 数据请求预算恶化（东财请求数明显高于既往常规、或 kamt 探针开始 FAIL = 频控升级信号）
- 预注册节点临近或已漂移（季度重估 09-26、Forecast Lab 各阶段闸门等）
- 预注册登记表触发（只读 `deploy/preregistered_items.md`，见下方细则）

**预注册浮出细则（2026-09-11 接入）**：

- 每次执行只读该文件，只看状态含 🟡（已登记/未实现）的条目，不改写该文件。
- 对每个 🟡 条目，从本次已收集的运行证据里判断其「触发条件」是否已满足（只允许使用已有证据：当日 daily_runs 小节、shadow_actions.jsonl 末行、新生成的 output/ 报告文件名；**禁止为此新增数据请求或运行 QuantV1 脚本**）。
- 例：`PR-20260911-01` 的触发 = 存在任何净值日收益类回测/因子验证的样本区间触及 2018-06-26 ~ 2019-07-17（证据如 `backtest_*.py` 新报告中的区间日期、shadow/晨检里提到的回放窗口）。
- 触发已满足 → 按待拍板格式入列，紧迫度标「中」，正文引用条目 ID + 一句话处置提醒，不展开重述登记全文（细节让 Summer 查登记文件）。
- 未触发 → 不入列，不进「需人工介入」行。
- 浮出后的状态推进（🟡→🔴 等）只能由 Summer 拍板后人工改写，本任务不得自行改状态。

**不入列**：单日 FAIL 且既有协议已有处置路径（如次日 21:30 自动补拉）、幂等跳过等正常现象——只进「需人工介入」一行，不上升到拍板。

**去重**：多日复现的同一问题合并为一条，标注「连续 N 日」。

**数量上限：每天最多 3 条**；超过时按紧迫度取前 3，其余并入最后一条「其他：<一句话清单>」。预注册浮出项同样占用该额度；多条并存时按紧迫度高→低排序，同紧迫度下新异常优先于预注册项；预注册项不得被静默丢弃（最多降入「其他」行）。

**格式**（写入汇总小节末尾；难以取舍的才展开利弊，一眼可断的用短格式）：

```
### 待拍板

1. **<事项标题>**（紧迫度：高/中/低）
   - 现状：<1-2 句，引用日期+数字事实>
   - 方案 A：<一句话> — 利：<一句话>；弊：<一句话>
   - 方案 B：<一句话> — 利：<一句话>；弊：<一句话>
   - **建议：A**。<理由 1-2 句，必须从长期视角：数据通道健壮性 / 维护成本 / 研究纪律（预注册、paper-only）/ 可回溯性 / 避免短期 hack 沉积技术债 中选 1-2 个说，不写「省事」「快」这类短期理由>

2. **<事项标题>**（紧迫度：…）
   - 现状：<一句话> → **建议：<具体做法>**（<一句理由>）

（无事项时整段替换为一行：待拍板：无）
```

## 第五步 最终回复（用户当天唯一要看的一条，务必精简）

- 整条控制在 10 行内；待拍板超过 3 条时仍是「3 条 + 其他」结构，不展开
